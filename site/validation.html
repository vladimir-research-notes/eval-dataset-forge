Validation & redaction

Audit dimension #1: is the data well-formed and safe to ship? Every later stage assumes it is operating on schema-valid examples, so validation runs first — strict about structure, explicit about the limits of its heuristic safety checks.

What it checks

* Personal-identifier findings are warnings by default and promoted to errors under --fail-on-pii; unambiguous secret findings are always errors — a benchmark should never ship a credential. The exit code is non-zero iff at least one error is present; warnings never change it.

How it works

Parsing is deliberately lenient: where the Milestone 2 loader raises on the first bad record, the validate command reports every problem across a file in one pass. A malformed JSONL line, a schema violation, and a duplicate id are all collected and addressed by a 1-based record ordinal, so a message points at the right line regardless of what failed before it.

The safety detectors are pattern- and entropy-based. Named patterns (email, IPv4 with per-octet range validation, AKIA… access keys, PEM headers, keyword: value assignments) give high precision; a Shannon-entropy heuristic catches bare API-key-like tokens that no fixed pattern would. Overlapping matches are de-duplicated so a precise hit (an AWS key) suppresses the generic token candidate covering the same characters.

Redaction replaces each detected span with a typed placeholder (<EMAIL>, <TOKEN>, <SECRET>, …), right-to-left so indices stay valid. Report snippets are redacted before printing, so the raw value a finding flags never leaks into the terminal or a log. Nothing is auto-corrected in place; redaction is an opt-in utility (--redact-out).

Command

evalforge validate --dataset datasets/fixtures/qa_toy/examples.jsonl
evalforge validate --dataset data.jsonl --json                 # machine-readable
evalforge validate --dataset data.jsonl --fail-on-pii          # PII blocks too
evalforge validate --dataset data.jsonl --redact-out clean.jsonl

On the committed fixtures the command exits 0: they are schema-valid, uniquely keyed, and PII-free. Planted missing-label defects (an empty gold answer, e.g. qa-010) surface as empty_expected_output warnings; the deeper label analysis is the label audit.

Status

Implemented (Milestone 3). The validate CLI is wired; tests/test_validation.py covers each detector (positives and negatives), deterministic redaction, the no-leak snippet guarantee, every schema-error kind, duplicate-id detection, the quality warnings, the severity policy, and a safe-data check that every fixture scans clean.

Open questions / limitations

  • The token/phone detectors are the noisiest: a long high-entropy hash or a digit-heavy string can be flagged (false positive), and unusual formats can be missed (false negative). This is why bare-token/PII findings are warnings by default.
  • Detection is regex + entropy, not a trained model or a DLP system — it removes only what it recognizes. It is a project-local sanitizer, not a guarantee of privacy safety.
  • Quality here is surface-level only; conflicting / ambiguous / inconsistent labels and adjudication are the Milestone 6 label audit.
