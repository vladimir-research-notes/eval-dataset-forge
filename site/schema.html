Dataset schema

Typed, validated formats for examples, manifests, audits, and releases. Malformed data fails loudly at load time instead of silently corrupting an audit.

Why typed schemas

Schema validity is audit dimension #1. Every downstream check assumes it is operating on well-formed examples. The schemas are pydantic v2 models (src/eval_dataset_forge/schemas.py); SCHEMA_VERSION is bumped on any breaking change to the on-disk format.

Every model forbids unknown fields, so a misspelled key (expcted_output) is rejected at load time instead of being silently absorbed; free-form extension goes into the explicit metadata / labels dicts. Enums serialize to plain strings, so records round-trip through JSONL with no custom encoder. A few cheap cross-field validators reject structurally impossible records early — split ratios must sum to 1.0, a bootstrap interval must satisfy ci_low ≤ ci_high, and a release's example count must match its manifest. These catch structural defects; the later stages look for semantic ones.

Release bundle Milestone 10

datasets/releases/<dataset_id>_v<major.minor.patch>/
  examples.jsonl        the data (validated)
  manifest.json         DatasetManifest: hashes, splits, counts, audit summary, identities
  audit.json / audit.md AuditResult + human-readable report   (audit.md: M12)
  dataset_card.md       purpose, construction, known issues, non-goals   (M11)
  splits/{train,dev,test}.jsonl
  REPRODUCE.md          exact rebuild commands

DatasetManifest gained seven fields in Milestone 10 — additive, with defaults, so SCHEMA_VERSION is unchanged and pre-existing manifests still load:

fieldmeaning
content_idorder-independent digest of the examples, split excluded — are these the same examples?
eval_idthe same digest with each example's split folded in — are two reported scores comparable?
source_content_idpins the pre-exclusion corpus
tool_versionthe builder that produced the bundle
split_specstrategy, seed, ratios — provenance, not identity
excludedevery removed example, its reason, and the id of the member kept
dependenceblock structure (counts and size histogram), not effective_n

Both aggregate ids bind a purpose tag and SCHEMA_VERSION, so a content id can never be read as an eval id and a schema bump changes every id by construction. The bytes that are hashed sort their keys and strip whitespace; the bytes that are written preserve schema field order, because a human reads them. manifest.json is excluded from its own hashes map — a file cannot contain its own digest. Fixture datasets Milestone 2

Five small, synthetic datasets under datasets/fixtures/ exercise the schema and, deliberately, break it in semantic (not structural) ways so the audit stages have real defects to find. Each is a directory with examples.jsonl, a machine-readable defects.yaml (ground truth of the planted defects), and a README.md.

fixturefamilynplanted defects
qa_toyqa14exact/paraphrase duplicates, mislabeled answer, ambiguous questions, missing & conflicting labels, train/test overlap, answer-in-prompt, duplicate source
agent_tasks_toyagent_task12near/exact duplicates, leaked solution in prompt, ambiguous scoring, missing/conflicting/inconsistent-format labels
retrieval_toyretrieval10near-duplicate query, duplicated & paraphrased docs, label-artifact contamination, incomplete relevance, over-specific query
bio_toybio10exact/near duplicates, conflicting entity labels, ambiguous & missing labels, mislabeled answer (non-clinical)
safety_toysafety10duplicates, over-refusal mislabel, ambiguous boundary, conflicting/missing/inconsistent labels — unsafe items are placeholders only

Defects no heuristic can catch — a well-formed but factually wrong gold answer — are marked auto_detectable: false in defects.yaml and excluded from audit-recall scoring, an explicit limitation rather than a hidden gap. scripts/validate_fixtures.py checks structural validity; tests/test_fixtures.py also verifies the ground truth matches the data.

Finding & result types

AuditResult aggregates DeduplicationFinding, LeakageFinding, LabelAuditFinding, PII flags, DifficultyScores, split statistics, and prioritized recommendations. SplitSpec, BootstrapResult, and DatasetCard complete the model set.

Status

Implemented (Milestone 1). All eleven models — DatasetExample, the three finding types, SplitSpec, DifficultyScore, BootstrapResult, AuditResult, DatasetManifest, DatasetCard, and DatasetRelease — are pydantic v2 classes in schemas.py. tests/test_schemas.py locks the DatasetExample field set, exercises strict rejection of unknown / missing / malformed fields, and asserts a JSON dump→reload round-trip for every model. The validate CLI that enforces this schema over a whole file — plus ID-uniqueness, quality, and PII/secret checks — landed in Milestone 3; see the Validation page.

Open questions / limitations

  • task_family is an open string vocabulary (not an enum); unknown families are a validation-layer warning (Milestone 3), not a schema error.
  • These models check structure, not meaning. A well-formed example with a wrong gold answer passes here and is caught downstream by the label audit.
