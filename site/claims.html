Auditing the documentation

Every other stage of this project audits a dataset. This one audits the prose, and Milestone 13 supplied the reason by accident. A generated artifact is enforced by a test. Prose is not. A claim written in Markdown has no way to fail, so it does not fail, so it rots.

The headline. Milestone 13 measured that a release is not reproducible from its inputs and seed alone — the build environment is an input — and corrected the sentence that said otherwise in exactly one file: REPRODUCE.md, which is generated and pinned by a test. The identical false sentence survived untouched in README.md, docs/METHODOLOGY.md, and docs/PLAN.md: three files no test had ever read.

What the auditor checks

python3 scripts/verify_docs.py runs 11 checks over the live documents, the historical record, and the module tree: every relative Markdown link, every shell command in a fenced block, 12 registered numeric claims, and — as of Milestone 15 — every module the docs/PLAN.md §4 architecture diagram names. It prints its own coverage and exits 1 when any documented claim is unsupported.

A diagram can name code that was never written

The first ten checks read what the docs say. None read what the tree is, so a package could be drawn in the architecture diagram and never built, and every check stayed green. Milestone 15's package-layout check found exactly that: docs/PLAN.md §4 declared an adapters/ package with mock_llm.py and api_stub.py, carried since the Milestone 0 scaffold, and no such package exists. The pipeline is entirely heuristic and calls no model, so no labeler adapter was ever needed; the diagram was corrected, not back-filled with dead code.

The check is one-directional on purpose. It flags a module the diagram declares and the tree lacks; it is silent about a module the tree holds and the diagram omits, because a layout diagram is a curated sketch. It proves the diagram names no vaporware; it does not prove the diagram is complete, for the same reason retired-claims cannot measure recall over false sentences.

Live documents and historical records are different things

README.md and docs/*.md state what is true now. docs/milestones/*.md and docs/review_notes/*.md state what was true at a commit — docs/milestones/12-smoke-audit.md records # 1706 tests and is right about the commit it describes. Checking counts against history would force rewriting the record to match the present, which is the one thing a record must never do. So counts and retired claims are checked against live docs only; links, commands, and referenced paths must work wherever they appear.

Use is not mention

Limitations contains the retired sentence on purpose, in order to say it is false. A lint that cannot tell an assertion from a quotation would either flag the correction or need an allowlist naming every file permitted to discuss the topic. The rule is the one English uses: a retired claim inside double quotes is mentioned; anywhere else it is asserted.

Two refinements were forced by real false positives, each found by running the checker rather than reasoning about it:

  • The unit is the paragraph, not the line. docs/RESULTS.md opens its quotation on one line and closes it on the next, and the first draft — which counted quotes per line — flagged the continuation as an assertion. It produced its only false positive on the document most careful to disown the claim.
  • Code spans are masked first. docs/DATASET_CARD.md contains a literal [text](url) inside backticks, as an example of the Markdown the card generator must escape. The link checker chased it to a file named url. That is the same use/mention error one level down, for links rather than sentences.

The cited_in escape hatch — files allowed to assert a retired claim anyway — is empty, and an allowlist that stays empty is one nobody can quietly grow.

A number is not a claim until it names the command that produced it

docs/RESULTS.md reports the qa_toy difficulty calibration p-value as 0.789. Running evalforge audit on the same fixture, at the same seed, prints 0.777.

command--resamples defaultpermutation p
evalforge difficulty100000.789
evalforge audit20000.777

Same fixture, same seed, same statistic (ρ = −0.080 in both). Neither number is wrong; the gap is the permutation test's Monte-Carlo error, which shrinks like 1/√B. A reader comparing the two documents has no way to discover why they differ. So every claim carries the command that produces it, and check_claim_commands verifies that column names a command that exists.

That check earned its keep immediately. The first draft of pooled_blocks_jaccard cited evalforge audit --near-method jaccard — a flag nobody had built. docs/RESULTS.md and Deduplication have published Jaccard recall and block counts since Milestone 4, and the only way to reproduce them was to uninstall scikit-learn. Milestone 14 added --near-method {auto,tfidf,jaccard}, so a published number can be reproduced without reproducing the environment that produced it.

One rule, registered and not enforced

sklearn_is_an_accelerator is a true proposition to retire: docs/PLAN.md §3 called scikit-learn an optional accelerator with a pure-Python fallback, and Milestone 13 showed it is a different detector. The rule ships in CANDIDATE_RETIRED_CLAIMS, enforced nowhere, with a test asserting nothing picks it up — the precedent being Milestone 13's difficulty_is_calibrated, registered and in no profile.

The reason is measured. Run against the live documents as Milestone 14 found them:

countwhich
documents flagged2LIMITATIONS.md, RESULTS.md
flagged documents that assert it0both quote it in order to refute it
documents that do assert it1PLAN.md §3
of those, flagged0the phrase spans a line break the pattern cannot cross

Precision 0/2, recall 0/1. The rule flags exactly the two documents that disown the claim and misses the one that makes it, because a correction must use the same words as the error. PLAN.md §3 and the pyproject.toml comment were fixed by reading them. Run against the corrected documents the rule flags three, and the third is this very page's source, docs/CLAIMS.md — the document that exists to explain why the rule is disabled.

The auditor is a defect detector, and it is scored like one

A checker reporting zero violations is indistinguishable, on that number alone, from a checker that looks at nothing — the mirror image of the flag-everything control in Results. So tests/test_docs.py plants a defect for every check and asserts the check fires: a broken link, an invented subcommand, a renamed flag, a stale count, a fixture id no fixture holds, a retired claim retyped, a ledger row the code does not reproduce, a drifted README, a claim citing a command that does not exist, an orphaned entry point, a layout that names a module the tree lacks. The hygiene scan (tests/test_hygiene.py) is scored the same way — each check is shown to fire on a planted forbidden path, forced-in file, or oversized blob.

Implementation

  • src/eval_dataset_forge/docs_audit.py — the 11 checks (CHECK_NAMES), the claim registry, the retired-claim ledger, and observe_numbers(), which recomputes every claim from the code and the committed artifacts and reads no document.
  • scripts/verify_docs.py — the runner; exit 1 on any unsupported claim.
  • tests/test_docs.py — 81 tests, of which the load-bearing ones are the controls.
  • docs/CLAIMS.md — the ledger and the full argument.

Limitations & open questions

  • It does not check that the code is correct. The ledger proves the documentation agrees with the code. That the code is right is what the rest of the test suite is for. A number can be wrong in both places and pass every check here.
  • Retired claims are matched as phrasings, not propositions. A paraphrase evades the pattern. Recall over "false sentences in this repository" is not measurable, because unlike the fixtures — whose defects are planted and enumerated — no ground-truth list of false sentences exists.
  • Only fenced shell blocks are parsed. An evalforge invocation written inline in prose is not checked.
  • evalforge is never executed. It exists on PATH only after pip install -e ., which the offline suite does not do. The entry-point check verifies the declared target imports and is callable; it does not prove the binary runs.
  • This website is not audited. The checks read Markdown. These pages duplicate the docs' claims in HTML, and nothing verifies that they agree — a gap raised for review rather than quietly closed.
