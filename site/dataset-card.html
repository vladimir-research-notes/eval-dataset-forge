Dataset card generator

A dataset card is the document a reader consults before trusting a benchmark. The failure mode it exists to prevent is not absence — most datasets ship a README — it is drift: a card written by hand in week one, describing a corpus that has been re-cut four times since, with a "known issues" section listing the issues someone remembered.

So the card is derived. build_card takes exactly two inputs — a release's manifest.json and its audit.json — and every count it prints is read from them. Nothing is recomputed. Re-running the dedup ladder at render time would let a threshold move between the audit and the card, and the card would then disagree with the audit.json sitting beside it in the same directory. A card is a view of the evidence, and a view that recomputes its own source is not a view.

1. Two things the card cannot print — by arithmetic, not taste

dataset_card.md is an artifact of the release, hashed into manifest.hashes alongside examples.jsonl and the split files. Two fields every dataset card in the wild carries therefore become impossible.

absent fieldwhy it cannot exist
the file-hash table The digest of the card's bytes would have to appear inside the card's bytes. That is a preimage requirement, not a design choice.
created_at A clock inside a hashed artifact makes every rebuild differ from every other, which collapses the none version bump — "nothing changed but the clock" — that Milestone 10 defined.

What the card prints instead are content_id and eval_id, which are functions of the examples rather than of the card, plus a pointer to verify-release for byte integrity. Both absences are pinned by tests that mutate every hash, and rebuild at two different clocks, and assert the card does not move.

This forces an order on the release builder. The card is rendered from a manifest, and its digest belongs in that manifest. So the builder assembles the manifest twice: once over {examples, splits, audit.json, REPRODUCE.md} so the card has something to render from, then again with the card's bytes in the artifact set. The two differ in hashes and nothing else — precisely the field build_card refuses to read. Were that not true, the shipped card would describe a manifest that was thrown away.
two builds of qa_toy, created_at 2020-01-01 vs 2031-12-31, everything else fixed

  same    audit.json          same    splits/{train,dev,test}.jsonl
  DIFFER  manifest.json

2. The headline number is two numbers

Milestone 10 left this open: "a card that says '14 examples' when the corpus holds 11 independent blocks is not lying, but it is not helping." The card prints both. A reader spends the headline number as a sample size, and 14 is not the sample size of anything.

And it goes one step further, because neither number bounds the claim a reader usually wants to make. A confidence interval on a test score is governed by the number of independent blocks in the test split. So manifest.dependence gained blocks_by_split and straddling_block_count:

splitexamplesindependent blocksshare
dev117.1%
test2214.3%
train11878.6%

A block straddling a split boundary is counted in every split it reaches, so the per-split counts sum to at least block_count, and straddling_block_count says by how much. Under the adversarial strategy it is zero. Under random it is not — and it is the same defect residual_overlap reports, counted differently.

3. Zeros go in the table, never in the bullets

The findings table lists every audit dimension, including the ones that fired zero times, with a certainty column. A zero on a heuristic row says the check found nothing — not that there is nothing to find. And a zero must be visible at all: a card listing only what was found is indistinguishable from a card whose pipeline never ran that check.

dimensioncountcertainty
duplicates: exact1exact
duplicates: near1heuristic (tfidf)
leakage: answer in prompt1heuristic
leakage: n-gram overlap0exact given the n-gram width
labels: needs adjudication4derived from the rows above
PII-like patterns0heuristic (pattern match)

The "Known issues" bullets carry only the non-zero findings, with example ids. A bullet reading "0 duplicates" is a reassurance; a table row reading 0 is a statement about what was checked. When every dimension is zero, the card says so without claiming the data is clean.

4. Curator prose: absent, never invented

Four sections cannot be computed from any audit, because they are claims about intent: purpose, construction, recommended_use, non_goals. They are supplied in a YAML file, validated (unknown fields rejected — a non_goal: typo raises rather than silently dropping the curator's non-goals), and recorded in manifest.card_meta — not read from a side file at render time, because a card whose text lived outside the release could not be checked against the release.

A section the curator left blank is named in the rendered card, never quietly omitted: a reader must be able to tell "no restrictions" from "nobody wrote any down". dataset-card --fail-on-incomplete lets CI insist on the difference.

Rewriting a non-goal changes no number and cannot move a score, so prose is packaging:

delta: 0.1.0 → 0.1.1 (patch bump; scores still comparable)
  content_id : same
  eval_id    : same
  - packaging only: hashes, card_meta

5. --check and verify-release answer different questions

commandquestiondepends on
verify-releaseAre the bytes on disk the bytes the manifest describes?the release directory alone
dataset-card --checkDoes this tool version still render the card that shipped?the release and the renderer

verify-release already covers the card's integrity — it is in manifest.hashes, so a corrupted card fails hashes_match like any other artifact. Folding the render check into it would make an old, perfectly intact release fail verification on the day the card's wording improved, turning a byte-integrity check that any reader can run into a claim about this repository's renderer. A test constructs exactly that case: a card edited and its hash updated. verify-release passes; --check fails and says the renderer changed, not that the release is corrupt.

6. One document, two backends

Markdown and HTML are not two templates. A report is built once as a Document — a flat list of headings, paragraphs, bullets, tables, notes, and code blocks — and rendered twice. Two templates are two places a number is written down, and the second one is where it goes stale. A test walks the document and asserts every string it carries reaches both outputs; no template pair can offer that.

The inline vocabulary is one item long: a code span. Bold, links, and nested emphasis would need a Markdown parser in each backend, and the dependency budget has no room for one. The cost is that a card cannot link out.

Escaping is a correctness property. The card interpolates untrusted text: license_notes, curator prose, and example ids from a JSONL file someone else wrote.
  • Markdown escapes \ ` | * < [ uniformly, in every literal span rather than only inside table cells. A contextual escaper has to know which block it is in, and the one time it guesses wrong is on a dataset whose license_notes contains a | — at which point the card's table silently grows a column.
  • < and [ are escaped because CommonMark passes raw HTML through, and [text](url) would become a live link the curator never wrote.
  • Intraword _ is not escaped: CommonMark already forbids it from opening emphasis, and a backslash in qa_toy would land in the most-read line of every card. _emphasis_ at a word boundary still is.
  • A line-initial 1. escapes the dot, not the digit — \1. renders as a literal backslash and still opens an ordered list, because CommonMark only recognizes an escape before ASCII punctuation. This was a real bug, caught by a test.
  • HTML escapes every literal span, and <title> gets a plain rendering: a <code> element inside <title> is not markup, it is six literal characters in the browser tab.
The generated HTML page is standalone: one file, inline stylesheet, no scripts, no fonts, no network. A dataset card should not require a server, and it should not be able to phone one.

## Known issues

- 1 exact duplicate cluster(s) — identical input and gold answer: `qa-001 + qa-002`.
- 1 near-duplicate cluster(s) above the tfidf threshold: `qa-003 + qa-004 + qa-012`.
  Heuristic — a paraphrase below the threshold is not here.
- 1 answer-in-prompt finding(s) covering 1 example(s): `qa-007`.
- 4 example(s) are quarantined in `train` because their gold answer is missing,
  conflicting, or unadjudicated. They are not deleted.

## Where these numbers came from

Generated facts are read from `manifest.json` and `audit.json`; prose is the curator's,
recorded in `manifest.card_meta`. 4 of 4 curator sections are supplied.

- This card prints no file hashes. It is itself hashed into `manifest.hashes`, so a
  digest of its own bytes cannot appear inside them.
- This card prints no build timestamp. A clock inside a hashed artifact would make each
  rebuild differ from the last, and a rebuild that changes nothing must be able to say so.
Honest negatives.
  • The card is a rendering of evidence, not evidence. audit.json is what a tool should read; the card is what a person should read. When they disagree, the card is wrong by construction, and --check says so.
  • Its counts inherit every upstream bound. A heuristic row is a lower bound. ret-001/ret-002 is invisible to the audit, so it is invisible here.
  • Four sections are unverified claims. Nothing checks whether the curator's prose is true. A release whose curator wrote "suitable for clinical use" would render that sentence faithfully.
  • It cannot conditionally warn about the difficulty buckets. AuditResult records the difficulty distribution but not the calibration verdict, so the card carries an unconditional note. The verdict does reach the reader — through known_limitations and recommendations, printed verbatim — but two sections away from the table it qualifies.
  • HTML is not part of the release bundle. A second rendering of the same facts inside a hashed bundle doubles the surface that can go stale and adds no information.

Status

Implemented in Milestone 11. 1659 tests pass (1595 prior + 64 reports). The committed demo release ships a generated card that regenerates byte-for-byte from its own manifest.json + audit.json; two builds at different clocks differ in manifest.json and nothing else. audit.md is still missing from the bundle, and every REPRODUCE.md says so and names the milestone that lands it (12).

Open questions

  • Should AuditResult record the difficulty calibration verdict, not just the distribution? It would let the card's note become a conditional warning. It would also be a schema change made for a rendering convenience.
  • Should the card quote the examples.jsonl digest? It is non-circular (only the card's own digest is impossible) and would let a reader with just the card verify the data. It would also re-introduce a file hash into a document whose thesis is that file hashes answer the wrong question.
  • Is --fail-on-incomplete the right gate? It measures whether four fields are non-empty, which a curator can satisfy with the word "TBD".
  • The card cannot link out, because the inline vocabulary has no link node. A card that could link to DEDUPLICATION.md would be more useful — and would need a URL policy for a file that may be read from a release directory, a repository, or a web page.
  • Should a release ship dataset_card.json (the DatasetCard model) so a tool can read the card without parsing Markdown? Today audit.json plus manifest.json already carry every fact, and the card adds only arrangement.
