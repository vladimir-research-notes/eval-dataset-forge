Example dataset card

Every release ships a dataset card: what the data is for, how it was built, what is known to be wrong with it, and what it must not be used for. Below is the shape of a generated card (illustrative — the real one is produced from an actual audit).

# Dataset card — qa_toy v0.1

## Purpose
Synthetic QA benchmark fixture used to exercise the audit pipeline.

## Construction
Hand-authored examples with deliberately planted defects (duplicates,
paraphrases, mislabeled answers, ambiguous questions, train/test overlap).

## Schema
DatasetExample (see docs/DATASET_SCHEMA.md). SCHEMA_VERSION 0.1.0.

## Splits
train N · dev N · test N — strategy: adversarial (near-dup aware), seed 7.

## Known issues (from the audit)
- exact duplicates: k
- near-duplicates: k (Jaccard ≥ 0.8)
- leakage flags: k (answer-in-prompt, train/test overlap)
- label warnings: k (conflicting, ambiguous)
- PII flags: 0

## Difficulty distribution
easy N · medium N · hard N

## Recommended use
Testing dataset-audit tooling. NOT a measure of real QA capability.

## Non-goals
Not a certification of quality. Not medical/legal/security guidance.
The card is generated from the AuditResult and DatasetManifest, so its "known issues" section is always consistent with what the pipeline actually found — no hand-maintained claims.
