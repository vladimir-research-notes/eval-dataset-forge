M12

The audit pipeline

A linear sequence of separable, independently tested stages. Validated examples in; typed findings, distribution summaries, and prioritized recommendations out.

Stages

load → validate → dedup → leakage → label-audit → difficulty
     → splits → statistics → report → release
stagewhat it checksexact / heuristic
validate M3schema, ID uniqueness, PII/secrets, qualityexact + heuristic
dedup M4exact, normalized, near-duplicateexact + heuristic
leakage M5train/test overlap, answer-in-prompt, n-gram, retrievalexact + heuristic
label-audit M6missing, conflicting, ambiguous, format, adjudicationexact + heuristic
difficulty M8surface score, buckets, and a calibration verdict on the score itselfheuristic — and uncalibrated on these fixtures
splits M7sizes, distributions, residual cross-split leakageexact, given the dedup clusters
statistics M9bootstrap CIs, paired comparison, ranking stability, small-N warningsresampling — cluster-aware, and a lower bound on the dependence
release M10manifest, content hashes, two dataset identities, re-run audit, REPRODUCE.mdexact — but every count it carries is a lower bound

The release stage applies any exclusions first and then runs the whole ladder again over the survivors, because dropping one member of an exact pair dissolves the cluster: an audit computed before the drop would describe a defect the release does not have.

Design principles

  • Findings, not verdicts. The pipeline never silently mutates data or certifies a dataset as "clean" — it emits findings and recommendations for a human to act on.
  • Exact vs. heuristic is always labelled. Every finding records the method used and (for heuristics) the measured score.
  • Determinism. Fixed input + seed ⇒ reproducible output.
  • Offline & CPU-only. No stage needs a network or GPU.

Status

Seven stages are implemented: validate (M3), dedup (M4), leakage (M5), label-audit (M6), splits (M7), difficulty (M8), and statistics (M9). The stages are separable but not independent, and the couplings are load-bearing: leakage consumes the dedup ladder's clusters to find cross-split overlap; splits re-runs those same leakage checks over its own output to verify what it built; difficulty inherits a defect from label-audit — an example with a missing gold answer scores at the floor of the output-complexity signal and therefore looks easy; and statistics resamples the very blocks splits builds, because a duplicate cluster is not an independent example and a confidence interval that pretends otherwise is too narrow. The audit pipeline passes one dedup report through rather than paying for the ladder repeatedly.

Two couplings run the other way, as inherited bounds rather than inherited data. The adversarial split's zero-leakage guarantee is exactly as strong as the near-duplicate stage's recall; and for the same reason the statistics stage's design effect is a lower bound — dependence the dedup ladder cannot see produces no block, so it cannot widen an interval either.

Milestone 10 publishes the audit beside the data it describes, and Milestone 11 renders it for a human as a dataset card — generated from manifest.json and audit.json, recomputing nothing, so a card and the evidence in the same directory cannot disagree.

Running it M12

PYTHONPATH=src python3 -m eval_dataset_forge audit \
    --dataset datasets/fixtures/qa_toy/examples.jsonl \
    --out results/audits/qa_toy/          # writes audit.json + audit.md

evalforge audit assembles every stage above into one AuditResult and renders audit.md from it — a pure view, reading no examples and no manifest, so the report cannot describe a defect the JSON beside it does not. The same assemble_audit serves the release builder; the two differ only in split_statistics.source (constructed vs observed), so a reader can tell a residual_overlap: 0 earned by the adversarial strategy from one a curator handed us.

An audit describes the split it is given, and never builds one. Re-splitting inside an audit would make the report describe a dataset that exists nowhere on disk. The consequence: on an unsplit corpus, four of the pipeline's signals — cross-split duplicate overlap, cross-split source reuse, n-gram containment against the train reference, and the dev/test duplicate count — return zero by vacuity, not by cleanliness. The audit names all four in a warning, in a recommendation, and in audit.md. A check that could not run is not a check that passed.

evalforge smoke runs the whole pipeline over every fixture and the pooled corpus, then scores the findings against each fixture's planted ground truth — beside a flag-everything control that shows what an uninformative answer scores under the same rule. See Results.
