Integration contracts

Five adjacent projects want to consume audited releases. None of them is a dependency of this package and none exists in this repository. What is committed is the shape of the question each one asks — executable, tested against the fixtures, and versioned. Writing those questions down turned up four properties of the pipeline that no earlier milestone had stated. Two were defects in claims the repo was already making; one was a defect in this milestone's own first draft, caught by checking a docstring rather than shipping it.

The headline. scikit-learn is documented as an optional accelerator with a pure-Python fallback. It is not an accelerator — it is a different detector. Rebuilding bio_toy from identical bytes, an identical command and an identical seed yields the same content_id and a different eval_id, a different held-out set, and 9 independent blocks instead of 8, purely because the package was importable. REPRODUCE.md claimed the build was "deterministic given the same inputs and seed". The environment is an input.

1. An audit has no opinion; a gate does

audit.json reports that qa-007 quotes its gold answer inside its own prompt. It does not say whether that is disqualifying, because the answer depends on who is asking. A retrieval benchmark measuring passage ranking may not care; a code-agent runtime about to gate a deployment on that benchmark cares a great deal. So the threshold lives with the consumer, in a reviewable GatePolicy, never in the release. A release carrying its own pass/fail verdict would be a dataset grading itself.

evalforge gate --release datasets/releases/qa_toy_v0.1.0 --profile code-agent-runtime

Exit 0 when the gate passes, 1 when it does not, 2 on a usage error.

Three verdicts, not two

verdictmeaning
passthe check ran on data it could act on, and found nothing
failthe check ran and found something
undecidablethe check could not run, or the release does not carry the evidence

Milestone 12 established that on an unsplit corpus four leakage signals return zero by vacuity, and printed a warning beside them. A warning is advice. A boolean gate that maps leakage_flags == [] → pass silently converts vacuity into permission. So undecidable is a distinct value, it never counts as a pass, and a policy that proceeds anyway must set allow_undecidable: true where a reviewer can see it.

Two requirements reach it, for two different reasons, and the difference is worth keeping:

  • no_retrieval_contamination on qa_toy — no example carries metadata.retrieval.docs, so the check inspected nothing. It is decidable on retrieval_toy. A fact about the corpus.
  • difficulty_is_calibrated on every release this tool has ever built — Milestone 8 runs a permutation test asking whether the difficulty heuristic beats a random ranking; Milestone 10 renders the answer as an English sentence; audit.json keeps the three bucket counts and drops the verdict. A consumer can recover it only by pattern-matching prose. A fact about the release format. Milestone 11's review note already asked whether that field should exist; the contract does not discover the gap but makes it executable, and adds a second reason to close it — besides forcing the dataset card to print an unconditional caveat, it denies every consumer a verdict. The requirement ships in the registry and in no profile.

audit.json records what each check found. It does not record what each check was given. Zero findings over zero passages and zero findings over a thousand clean passages serialize identically.

2. Three identities, three consumer-side scopes

Milestone 10 gave a release three identities because a file hash answers the wrong question. Each turns out to be the scope of exactly one downstream claim.

identityscopesa consumer that ignores it
content_ida content-scoped gate verdict reuses a verdict on a corpus it was not computed on
eval_ida score, and a split-sensitive gate verdict compares two numbers measured on different held-out sets
dependence.near_methoda rebuild cannot reproduce the release it depends on

The third row is what this milestone had to discover; the second turned out to scope more than Milestone 10 assigned to it (§4).

The optional accelerator is a different detector

resolve_near_method("auto") returns tfidf if and only if scikit-learn is importable, and jaccard otherwise. The two disagree about which examples are duplicates. Duplicates become blocks; the adversarial split refuses to cut through a block; eval_id folds the split in. On bio_toy, bio-001 ≈ bio-002 clears the 0.30 threshold under idf weighting and not under raw set overlap. One pair, one threshold.

scikit-learn presentscikit-learn absent
near_methodtfidfjaccard
near-duplicate clusters10
independent blocks89
content_ididentical — they are the same examples
eval_iddifferent — they are not the same benchmark

content_id holding is correct, and eval_id moving is the tool telling the truth. What was false was REPRODUCE.md. Every release now records dependence.near_method and carries an Environment section naming it.

Verification is environment-independent; reproduction is not. verify-release recomputes every file hash and both identities from bytes and runs no detector, so a release built with the accelerator verifies at 10/10 on a machine without it. That asymmetry is the only reason a release built on one machine can be trusted on another — and it is why the open question "should verify-release re-run the audit?" now has an answer: no, it would make integrity depend on the verifier's pip list.

3. Two properties that do not hold under union

Both follow from one fact: TF-IDF's idf term is computed over the document collection, so a near-duplicate similarity is a property of a pair and its corpus. Milestone 12 measured it on sim(saf-004, saf-007): 0.2866 inside safety_toy, 0.3438 pooled, straddling the 0.30 threshold with neither prompt changed.

A gate verdict is not preserved under union

safety_toy alone reports one near-duplicate cluster and passes a max_near_duplicate_clusters: 1 policy. Concatenate it with the four other fixtures — which share not one duplicate with it — and the same ten rows report two clusters and fail. Merging two gated releases yields an ungated corpus. GateReport.applies_to() compares content_id and refuses to answer for any other; assert_applies_to() raises rather than warns.

Independent-block count is not additive, although example count is

the five fixtures, disjointexamplesindependent blocks
audited separately, summed (tfidf)5645
audited as one corpus (tfidf)5644
audited as one corpus (jaccard)5646

The pooled corpus contains zero cross-fixture duplicate edges. Merging five unrelated datasets found no duplicate between them and still changed one dataset's verdict inside itself: {saf-004, saf-005} grows to {saf-004, saf-005, saf-007}. Appending unrelated data can move an untouched example's block, hence its split, hence a release's eval_id.

Under jaccard, which has no idf, the counts are equal. Composability is a property of the similarity function, not of this repository's data — and the optional dependency is exactly what removes it. So a regression suite that doubles its example count has not necessarily bought √2 of anything, and evalforge stats --resample-unit block must be re-derived after any merge. Audit the corpus you will score on.

4. A third property that does not hold, for a different reason

content_id is not always enough. no_train_test_overlap, no_retrieval_contamination, eval_splits_deduplicated and eval_split_is_rankable read the split assignment, so their answers move when the seed does while content_id stands still. Building qa_toy forty times with --strategy random, one seed per build:

value
distinct content_ids across all 40 releases1
seeds that pass eval_splits_deduplicated9, 35
seeds that fail itthe other 38

A gate comparing content alone would hand seed 9's pass to seed 0's release — which is exactly what the first draft of this milestone's own API did, until the docstring claiming otherwise was checked. So a report is scoped to eval_id whenever a split-sensitive requirement ran and to content_id otherwise; GateReport.scope says which, and every rendered report names it. The scope is derived from the requirements that actually executed, never from the split strategy someone claims to have used: the adversarial strategy does hold all four at zero for every seed, and relying on that would be trusting a split_spec field to be true.

integrity sits outside the scheme entirely — it is a statement about the bytes of one directory, and two releases can share both identities while differing in created_at. A report is never evidence about a directory other than its own release_dir.

5. The five contracts

Each profile names its requirements and — at equal weight — two lists nothing else in this repository writes down: what the consumer must establish for itself, and what the profile deliberately does not check. An omission that goes unstated is indistinguishable from an oversight. Every profile begins with integrity and schema_compatible: a finding read out of a release whose bytes do not match its manifest is not a finding.

profilethe question it turns into an exit code
code-agent-runtimeare these tasks sound enough to gate a run on?
bioagentbenchis this synthetic biomedical set free of PII and label conflicts?
llm-regressioncan this suite rank two models at all?
scientific-claim-verifierare the claim/evidence labels consistent and unleaked?
agent-control-benchis this control set clean without being sanitized?

llm-regression counts blocks, never rows. eval_split_is_rankable reads dependence.blocks_by_split, because a duplicate cluster contributes m rows and one unit's worth of information (Milestone 9). A test split of 200 rows in 3 duplicate clusters is a test split of 3.

agent-control-bench does not require unambiguous labels. An over-refusal / under-refusal set exists to probe the ambiguous boundary, so an ambiguous label is a feature of the corpus. A profile requiring zero of them would reject every well-constructed control benchmark, safety_toy included.

What the demo release scores

qa_toy is a deliberately flawed fixture, so all five profiles reject the release built from it — a gate that passed it would be broken. The positive control lives in the test suite: a release built with --drop exact,normalized,blocking-labels passes.

6. The declared read set

A consumer that calls json.load(open("manifest.json")) has taken a dependency on every key in the file, including the ones it does not read, because nothing tells a reader which those are. So the reads are declared: MANIFEST_FIELDS, AUDIT_FIELDS, DEPENDENCE_FIELDS, SPLIT_STAT_FIELDS, SPLIT_COUNT_FIELDS are the entire surface, and a test asserts each name exists both on the pydantic model and in the committed demo release. Adding a key is a patch. Removing or retyping a declared key is a major, and CONTRACT_VERSION moves with it. Milestone 12 grew split_statistics by two keys under an unchanged SCHEMA_VERSION. That was legal and invisible. The test that would have caught the reverse now exists.

Status

Implemented. evalforge gate is the thirteenth subcommand; 50 tests cover the contracts, and the full suite is 1756, CPU-only and offline. Every number on this page is reproducible from the committed fixtures.

Open questions & limitations

  • No gate can ask the question that usually matters. Whether the model under test was trained on the benchmark is measurable only against text the auditor holds, and nobody holds a frontier model's training set. Every leakage check here is intra-corpus.
  • Should audit.json carry the difficulty calibration verdict? It is computed and discarded. Adding the field is a schema change; leaving it out means a permanently undecidable requirement. Not decided unilaterally.
  • Should near_method default to jaccard? TF-IDF dominates Jaccard on the fixtures at every threshold — and it is the reason a duplicate report does not compose. Choosing the weaker detector to buy composability is a real trade, and nothing here settles it.
  • min_eval_blocks = 30 is a convention, inherited from Milestone 9's MIN_EFFECTIVE_N, not a theorem. On a corpus with a 3.6-point margin, Milestone 9 measured that ≈4500 examples were needed.
  • The five profiles are written from the outside. None of the named projects has reviewed its own contract, so each is a plausible reading of what that consumer needs, not an agreed interface.
