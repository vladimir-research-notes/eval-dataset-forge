Release builder & dataset identity

A release turns an audited corpus into a citable artifact: examples, splits, a manifest, an audit, and the command that regenerates all of it byte-for-byte. The hard part was never the packaging. It was working out what a release's identity should mean.

The headline. Two releases can hold identical data and produce incomparable numbers — and on this repository's own corpus, the difference is larger than the effect the benchmark exists to measure. Holding the data and every system's score vector fixed and varying only the split seed, the reported headline number moves with sd 0.130 against a top-two system gap of 0.036. A content hash cannot see any of it.

1. A file hash answers the wrong question

A digest over examples.jsonl changes when the dataset does not — reorder the rows, reformat the JSON, rebuild on a different clock — and holds still when the dataset's meaning moves, because re-cutting the splits leaves every byte of the corpus in place. So a release carries three identities, each answering a different question.

identityanswersconstruction
hashes[<file>]Did these bytes survive the trip? SHA-256 of the file as written
content_idAre these the same examples? Order-independent digest of the examples, split excluded
eval_idAre two reported scores comparable? The same digest with each example's split folded in

Both aggregate ids bind a purpose tag and SCHEMA_VERSION (domain separation), so a content id can never be read as an eval id, and a schema bump changes every id by construction. content_id sorts the per-example digests but does not deduplicate them: a corpus listing an example twice is not the corpus listing it once, which is the entire premise of Milestone 4.

Canonicalization is not serialization. The bytes that get hashed sort their keys and strip whitespace. The bytes that get written preserve schema field order, because a human reads them. Hashing the presentation form would make a dataset's identity depend on how its writer felt about field order.

2. The measurement behind eval_id

Hold the corpus fixed. Hold each system's per-example score vector fixed — generated once, never re-drawn. Vary only the split seed. Anything that moves is caused by the split. Pooled corpus: 56 examples, 44 independent blocks, 3 simulated systems, 400 seeds per strategy (scripts/split_identity_experiment.py).

The split seed is worth 3.6× the effect the benchmark measures, and which system "wins" is decided by the seed rather than by the systems. The mean over seeds recovers the corpus number (0.7011 vs 0.6964), so this is variance, not bias — an honest estimator of a quantity 11 examples cannot pin down. That is Milestone 9's problem. Milestone 10's problem is the corollary: a release identified only by its content would call all 400 of those releases the same.

3. A claim the measurements killed

The first draft of RELEASES.md said the adversarial strategy produces a better test split, pointing at its agreement rate: it reproduces the corpus ordering 65.0% of the time against random's 48.7%. The sub-population accuracies say otherwise.

adversarial evicts duplicate clusters from dev/test, and the duplicated examples are not a random subset — both systems score higher on them. Its test set therefore measures a sub-population whose true gap is nearly three times larger, and a larger true effect is easier to detect. Its higher agreement rate is a consequence of a different estimand, not of a lower-variance estimate of the same one. The tool records split_spec and eval_id so a reader can tell which question a number answers. It does not rank the strategies.

4. The version bump keys on the evaluation splits

bumpwhen
majoranything dev ∪ test can see — including a pure re-split
minortrain-only content changes
patchpackaging
nonethe clock

A pure re-split is major: the one verdict a curator finds surprising, and the reason the 400-seed experiment exists. There is no 0.x special case — the usual "below 1.0 anything goes" convention collapses major and minor exactly on the datasets most likely to be re-cut weekly, so 0.1.0 + major = 1.0.0. created_at reaches no hashed artifact; without that, none would be unreachable and patch meaningless. And the version cannot influence the bump that chose it: because audit.json and REPRODUCE.md embed the version string, the candidate manifest used for the delta is assembled at the previous version — otherwise every rebuild would report at least a patch on hash churn alone.

5. The audit describes the data that shipped

Exclusions are applied first, then the dedup / leakage / label / difficulty ladder runs again over the survivors. Dropping one member of an exact pair dissolves the cluster; a report computed before the drop would describe a defect the release does not have. Deletion is recorded, never silent: manifest.excluded names every removed example, its reason, and the id of the member kept, while source_content_id pins the pre-exclusion corpus. Nothing is dropped by default.

6. The question Milestone 9 left open

"Should the manifest record effective_n alongside example_count?" No. Since n_eff = n / (1 + (m̄ − 1)·ICC) and the ICC is a property of a scored comparison, it needs system scores — which a dataset does not have. A manifest quoting an effective_n would be quoting an assumed ICC and passing it off as a property of the data. So manifest.dependence records exactly what the computation needs and stops: block_count, block_size_histogram, duplicate_block_count, near_method, and a note pointing at --resample-unit block.

Commands

PYTHONPATH=src python3 -m eval_dataset_forge release \
  --dataset datasets/fixtures/qa_toy/examples.jsonl \
  --dataset-id qa_toy --version 0.1.0 --strategy adversarial --seed 0 \
  --quarantine-blocking --out datasets/releases/qa_toy_v0.1.0

PYTHONPATH=src python3 -m eval_dataset_forge verify-release \
  --release datasets/releases/qa_toy_v0.1.0

verify-release runs ten checks and prints the ones that passed — a verifier that only prints failures is indistinguishable from one that did nothing. It collects problems rather than raising, so one pass reports every defect.

Honest negatives.
  • verify-release detects accident, not an adversary. manifest.json cannot hash itself, so anyone able to rewrite the data can rewrite the digests describing it. Signing is out of scope and out of the dependency budget. test_verify_release_cannot_detect_a_rewritten_manifest asserts the hole rather than leaving it implied.
  • Every count in a release except the ids is a lower bound. block_count, the duplicate clusters, and the leakage flags all inherit Milestone 4's lexical recall bound. ret-001/ret-002 is invisible here too.
  • The minor bump is about score comparability, not benchmark validity. A train-only addition cannot move a fixed system's test score, but it can introduce train→test leakage that changes what that score measures for a system trained on the release. Every minor emits a warning saying so.
  • The delta joins on example_id. Renumbering ids without changing content reads as a full removal plus addition and forces a major. Conservative, and noisy.
  • eval_id is blind to a change of metric. It can say the arrangement moved. It cannot say the scoring function did, because a dataset does not carry one.
  • The committed demo release has a two-example test split. It is the honest output of the documented defaults on a 14-example fixture, and the release warns that its test split cannot measure hard. It demonstrates the format; it is not a benchmark.
  • The experiment's system scores are synthetic. No model runs offline. The block structure and the split strategies are real, and the claim is about the estimator rather than about any model. Nothing here is a statement about any real system.

Status

The committed demo release passes all ten checks; the command printed inside its own REPRODUCE.md regenerates it byte-for-byte, verified under several PYTHONHASHSEED values in separate interpreters. Open questions

  • Is major too blunt for an addition to test? Adding ten test examples does not invalidate an old score on the old test set; it makes the two numbers describe different sets. A separate "superset" level would say so — and would be a level nobody knows how to act on.
  • Should --drop near exist? It deletes real data on a heuristic this repo has already measured to have disputed false positives. It is off by default and fully recorded, but nothing stops a curator reaching for it because it makes the audit look clean.
  • content_id covers metadata and provenance. Arguably a note in metadata is not data — and arguably metadata.retrieval.docs very much is. No rule distinguishes them without a schema saying which keys are load-bearing.
  • The delta reads the previous release from disk, so --version auto is unavailable exactly when the previous release is hardest to obtain.
  • Should verify-release re-run the audit? Doing so would make verification cost a full audit and would silently re-run heuristics whose thresholds may have moved between tool versions — turning a byte-integrity check into a claim about method stability.
