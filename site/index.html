Milestone 5 — leakage & contamination

Make evaluation datasets trustworthy

A benchmark that reports one accuracy number hides most of what decides whether that number means anything. eval-dataset-forge turns duplication, leakage, label noise, split artifacts, difficulty imbalance, and unstable rankings into measured, reported properties of a dataset.

The problem

Two systems can be separated by a gap that vanishes under resampling. A "hard" test set can be trivially solved because the answer leaks into the prompt. A five-point gain can be an artifact of forty near-duplicate examples clustered in the test split. These are common, documented failure modes — and they are invisible in the JSONL file itself.

The idea

A benchmark dataset should not be a bare file. A trustworthy release is a dataset + evidence bundle:

1. Schema validation

Typed fields, ID uniqueness, metadata consistency.

2. Deduplication

Exact, normalized, and near-duplicate detection.

3. Leakage checks

Train/test overlap, answer-in-prompt, n-gram & retrieval contamination.

4. Label audit

Missing, conflicting, ambiguous, and inconsistent labels, plus an adjudication queue.

5. Difficulty calibration

Transparent, model-free difficulty proxy + distribution.

6. Split rationale

Random, stratified, source-grouped, adversarial, temporal.

7. Statistical uncertainty

Bootstrap CIs, paired comparison, ranking stability.

8. Dataset card + manifest

Purpose, known issues, non-goals, hashes, reproduce commands.

Architecture

raw examples → validate → dedup → leakage → label-audit → difficulty
             → splits → statistics → report → versioned release

Each stage is a separable, independently tested module. The pipeline is deterministic given a fixed input and seed, runs fully offline, and needs no GPU and no paid API.

Design constraints

  • CPU-first; runs on a general instance (e.g. m5.2xlarge).
  • Fully offline by default; no paid API anywhere in this version.
  • Small, honest dependency set (pydantic, numpy, pyyaml) with pure-Python fallbacks for optional accelerators.
  • Privacy-safe synthetic fixtures; redaction + PII-like detection built in.
  • Every heuristic documents its failure modes.

Status

The scaffold, plan, CLI, website, environment check, milestone runner, and CPU-only test suite are in place; the typed data contracts every stage builds on — the pydantic v2 schema models — landed in Milestone 1; Milestone 2 added five synthetic fixture datasets with deliberately planted defects and a machine-readable ground-truth file per fixture, so the audit stages can later be scored for recall against known defects; Milestone 3 landed the first pipeline stage — validation & redaction (schema, ID uniqueness, PII/secret detection, and typed-placeholder redaction), wiring the evalforge validate command; Milestone 4 added the second — deduplication, a three-stage exact / normalized / heuristic ladder whose near-duplicate thresholds are calibrated against the fixtures' planted paraphrases and whose two failure modes are pinned by regression tests; and Milestone 5 added the third — leakage & contamination, four deliberately non-disjoint channels (cross-split overlap, answer-in-prompt containment, reference n-gram overlap, retrieval contamination) that between them recover every planted leakage defect, including one the deduplication ladder is provably blind to. The remaining audit subsystems follow milestone by milestone — see Milestones and the docs/PLAN.md build contract.

This is a benchmark-quality instrument, not a certifier of universal benchmark quality and not a medical, legal, or security authority. See Limitations.
